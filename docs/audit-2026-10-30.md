# Audit of the handbook, 2026-10-30

What the handbook is for, what it does well, where it fails, and a plan to make it work. Written by
a session on this repository at the owner's request ("inspect it, audit it, suggest how to improve
it significantly and a strategy how to"). It changes no rule; every change it proposes is a question
in `docs/open-questions.md` (5 to 11). Measured on version 2026-10-30 of `HANDBOOK.md` (32,340
characters) and version 2026-10-27 of `PHASES.md` (16,639 characters).

## What it is for

- One public rulebook for every Claude Code session anyone at Kowboy starts, on any repository.
  The owner runs product work through chat; agents do all the engineering; four memory files per
  repository carry decisions from one session to the next.
- It reaches a session through one line in each person's personal preferences on claude.ai: the
  session downloads the file, reads it and follows it as it would a `CLAUDE.md`.
- It grows by correction: the second time the owner corrects the same thing, the correction becomes
  a rule with its date and the owner's words.

## What it does well

- The division of labour is clear and stated once: the agent leads, the owner decides.
- The reply protocol is designed around the reader's effort, and the register gives every question a
  number for good, so the owner can answer by number in any conversation.
- The "Stop and ask" gates, the live-site rule and the one-way-decision rule are sharp and testable.
- Cold pickup (2026-10-30) is the right principle for a one-person company with many agents.
- The change history is good: every save says what changed and why, with the owner's words.
- It has been condensed once already (2026-10-27, from 49,886 to 29,847 characters), so the team
  knows the problem and the method.

## Findings

Each finding has a letter and number so a question can point to it.

### A. Does it reach the session and stay there?

- **A1. It enters at the weakest level and is lost at the first compaction.** The platform's own
  instructions and the personal preferences come first. A `CLAUDE.md` is sent right after them,
  re-sent with every request and put back from disk after compaction (the platform summarising
  older parts of a long conversation to make room). The handbook, downloaded and read with a tool,
  is ordinary conversation: after compaction only a few recently changed files are read again, and
  a file over about 5,000 tokens comes back as a path without its content (a token is the unit a
  model reads, roughly four characters). The handbook is about 8,000 tokens. So in every long
  session the rules are gone from the first compaction on, while the
  platform's reply defaults stay whole, and the precedence the file claims in its first lines is a
  request to the model, not a mechanism. Verified against the platform's documentation on
  2026-10-30 (see "Delivery mechanisms" below). This explains "almost every session feels abandoned
  mid work" better than any rule does.
- **A2. The competing reply shapes were analysed and left in place.** Register question 1 (27
  October) named three competing formats: the platform's short replies, the preferences' "Output
  shape" (answer on line one, minimal bullets) and the handbook's blocks. Questions 3 and 4 were
  withdrawn in favour of an assertion in the file (A1). The preferences still carry the competing
  "Output shape", so every reply is written under two contradictory instructions. The path itself
  is undocumented: no page of the platform's documentation says the personal preferences reach a
  Claude Code session. It works today, as this session shows, but nothing guarantees it.
- **A3. The handshake is weak.** The first line reports the version and size, which proves the
  download, not the reading, and says nothing about `PHASES.md`. The version is a date; the three
  versions saved on 28 October were told apart with an improvised suffix, "(second)" and "(third)",
  that nothing enforces and the save messages do not always repeat.
- **A4. It costs about 12,000 tokens before any work and grows about 800 characters a day.** The
  two files are 48,979 characters together. Since
  the condense of 27 October the main file has grown from 29,847 to 32,340 characters in three days.
  At that rate it passes 50,000 characters again in about three weeks, and the condense has to be
  done again by December, by hand, with the same risk of losing a rule.

### B. Can an agent follow it?

- **B1. 124 bold-led rules is too many to hold at once.** 78 in `HANDBOOK.md`, 46 in `PHASES.md`,
  474 and 248 lines. The platform's own guidance for an instruction file is under 200 lines:
  "longer files consume more context and reduce adherence". A model follows a short list of sharp
  rules far better than a long list of good ones, and the
  rules that slip most (questions in prose, no number, going quiet, no state line) are reply-shape
  rules buried among rules about code, deletion and product texts that matter only while building.
- **B2. History is mixed into the rules.** The main file holds 47 dated attributions; the 41
  parentheses that carry a date hold 1,676 characters, all 84 parentheses 3,654, and the owner's
  quoted sentences sit inside them. They are valuable as history, but each makes
  the rule it sits in longer to parse and ties it to one anecdote. The handbook itself prescribes a
  `docs/decisions.md` for exactly this (date, decision, who decided, reference).
- **B3. Its own terms are not explained.** "Decide" is used as a noun about fifteen times and never
  defined; "Default" is defined only by example; "register", "staging", "converged state",
  "protected path", "gate", "golden master" and "expand, migrate, contract" are used before or
  without a definition. The handbook demands that every term be explained the first time it is used.
- **B4. Two of the four blocks have no example.** Questions and Done have one; Notes and Next have
  none, nor has a discussion-mode reply, and Next is the block the owner said was missing most.
- **B5. Always-on and when-needed rules are not separated.** "Principles and code" (with "Every
  text in the product"), "Checks" and "Definition of done" are 5,738 characters that matter only
  while building or reviewing and could sit in `PHASES.md` under Build and Review; the index of
  phases (1,166) could open `PHASES.md` instead. What must hold in every reply (who decides,
  working with the owner, the reply protocol, memory, several repositories, raising issues, twice
  is a rule, stop and ask, session, units of work) is 24,024 characters, plus a 1,396-character
  header.

### C. Is it consistent with itself?

- **C1. One pair of rules is left open.** "A clear winner is done, not offered" (7 and 23
  October) against "a question gets an answer, not a change" (29 September): when the owner asks
  whether something should be done and one answer is clearly best and safe, the first rule says do
  it and note it, the second says answer and wait for the word. The handbook does say that a gate
  from "Stop and ask" always wins and that visible things are such a gate, so the rest of the
  precedence is settled; this pair is not. One line settles it.
- **C2. A development tool that is also a library falls between two rules.** "Which tool, where a
  test runs, how something is built: never asked" against "a library or framework added, dropped or
  swapped: pause, propose and wait". A test runner, a bundler or a linter is both, so swapping one
  is tooling by the first rule and a gate by the second. One clause ("a tool that does not ship in
  the product is tooling") settles it.
- **C3. The numbering rule cannot be met where sessions run.** The rule of 28 October (a number is
  the question's only once it is saved to the converged copy) reversed the rule of 27 October within
  a day, and assumes every session can save to that copy mid-task. A session started on claude.ai
  works in a copy of its own that is combined into the shared copy later, and is told never to save
  anywhere else (this session included); a session on a client's repository has no access to this
  repository at all. The handbook already has the
  clause that resolves a duplicate when work is combined; the rule could rely on it.
- **C4. "Status" is defined twice**, in "Session" and in `PHASES.md`, with a small difference (the
  Done block needs what is in staging and not live, which no memory file holds).
- **C5. Rules repeated across the two files**: two failed fixes, look two items ahead, one
  component, market-leading (five times), protected path (six times), "memory current" in "Session"
  and in the header of `PHASES.md`. Each repeat is a place for the two copies to drift apart.
- **C6. The repository does not keep what it prescribes.** Every repository worked in for more than
  a session must keep four memory files; this one kept only the register until this audit, and the
  register's own header says an answered question "is recorded in the handbook's history", so the
  save history stands in for `docs/decisions.md`. A `docs/decisions.md` here is also the natural
  home for the history in B2.
- **C7. A first correction is lost between sessions.** "Twice is a rule" counts corrections, but a
  session on a client's repository cannot write to this register, and nothing else records a first
  correction. So most rules were written on one anecdote, and the clause that deletes a rule nobody
  would break has never fired in 31 saves.

### D. How is it maintained?

- **D1. No automatic check guards the file.** Nothing verifies that the file ends with its end
  line, stays under a size, has a new and unique version when it changes, or that a condense lost no
  rule (the 27 October check was done by hand by a fresh agent). Each proposed change is combined
  into the main copy within seconds of being opened, so the proposal is a formality, and every
  session fetches the main copy directly: one bad save reaches every session at once.
- **D2. The file only grows.** With no counter for corrections (C7) and no size budget, the
  reflex is to add. 31 saves in 33 days, all additive except one condense.
- **D3. No change log a session or the owner can read.** The save history carries it well, but a
  session cannot see what changed since the version it last worked under.
- **D4. The version is a date** (A3): a second change in one day gets a suffix by hand, or none.

### E. What is missing?

- **E1. Connected services and client data.** Sessions now carry many connected services (mail,
  files, chat, shops, accounting). Nothing says what an agent may read or send through them, or
  that a client's data never leaves the client's own systems. The only privacy rules are about logs
  and secrets.
- **E2. A budget for a session.** Beyond "two failed fixes" and "the search fits the choice" there
  is no limit on time, helper agents or cost before a session stops and reports.
- **E3. Language.** Which language product texts and documents are written in (and which spelling
  the handbook uses) is unstated. It belongs in each repository's `AGENTS.md`; the handbook should
  say so.
- **E4. The owner's word against the handbook.** "The owner decides" implies the owner's
  instruction in chat wins over a handbook rule; it is not said, and the conflict rule covers only
  decisions, strategy and acceptance criteria.

## The strategy

The aim, in the owner's words of 27 October: "it contains instructions and i want you to understand
and follow them. Make so it works". Working means: read whole, held for the whole session, short
enough to follow, and proven by a feedback loop rather than by hope. Six steps, in order; each is
an item in `docs/next-steps.md` of this repository, created with this audit, waiting on its
question.

1. **Restructure without changing a rule** (one session; the owner reads the result before it is
   saved). Question 5.
   - A core `HANDBOOK.md` of at most 20,000 characters and under 200 lines: who decides, working
     with the owner, the reply protocol with an example of every block and of a discussion reply,
     the memory files, several repositories, stop and ask, session, units of work, twice is a rule,
     a glossary and the two missing lines (C1, C2, E4). The arithmetic: 32,340 today, less 5,738 of
     build-time rules and 1,166 of phase index moved out, less about 2,500 of history, less about
     500 of repeats, plus about 1,500 of glossary and examples, is about 24,000; a wording pass
     that changes no rule brings it under 20,000. The owner reads the result before it is saved.
     Reaching 16,000, the most a claude.ai project's instructions can hold, takes a harder condense
     and is done only if question 11 lands on that channel.
   - The build-time rules (B5) move under Build and Review in `PHASES.md`, which stays under
     20,000 characters.
   - The history (B2) moves to a new `docs/decisions.md` here: one line per rule, with the date,
     the owner's words and the rule it created. The rule text stays; the parentheses go.
   - C3, C4 and C5 are fixed in the same change. A fresh agent checks, rule by rule, that nothing
     was lost, and its checklist is part of the proposed change.
2. **Fix the delivery** (one step for the owner, one session for the agent). Question 6.
   - The personal preferences stop describing a reply shape of their own and point to the
     handbook; the agent writes the replacement text and the owner pastes it (A2).
   - The core is delivered at the level of a `CLAUDE.md`, so it is re-sent every turn and survives
     compaction (A1): through the organisation's managed settings if the owner's plan offers them,
     otherwise through each project's instructions. Question 11; the channels and what each needs
     are in "Delivery mechanisms" below. The downloaded file stays as the fallback for every
     session type and carries the rest.
3. **Guard the repository** (one session). Question 7.
   - Automatic checks on every proposed change: the end line is present, each file is under its
     budget (core 20,000 characters and under 200 lines, phases 24,000), the version changed and is
     unique, the formatting is clean, and no e-mail address or web address other than this
     repository's slipped in.
   - The version becomes a date with a letter (2026-10-30a), and a `CHANGELOG.md` is kept so a
     session and the owner can read what changed since a version (D3, D4).
   - A proposed-change checklist: which correction or question asked for it, and the "no rule lost"
     check for a condense.
4. **Give "twice is a rule" a memory and a budget** (a rule, then one session a month). Question 8.
   - A first correction is written where the session can write: a dated one-line "Corrections"
     list in that repository's `AGENTS.md`, named as the handbook's own text already allows.
   - One handbook session a month reads those lists (the owner names the repositories or pastes
     the lists), promotes what appears twice, deletes rules nobody broke, and checks the budget:
     when the core is over its budget, something leaves before something enters.
5. **Prove it** (one session after each handbook change, optional). Ten scripted prompts with the
   reply shape each must produce (a working reply, a discussion reply, a question, a Default, a
   blocked session, "status"), run in a fresh session by a second agent, pass or fail recorded in
   the proposed change. The platform can run such cases automatically for a plugin (a package of
   instructions and tools installed on an account), with automatic checks of each reply's shape,
   if the core is packaged as a plugin for the test; by hand works too. It turns "the reply
   protocol slips" from a feeling into a count.
6. **Close the gaps** (one session). Questions 9 and 10 now; E2, E3 and E4 are folded into step 1
   as one line each.

Expected result: the always-on text halves, one reply shape instead of three, rules reach the
model at a level that survives a long session, and every month the file gets shorter where nobody
needed it and longer only where the owner corrected twice.

Risks: a rule lost in the move (met by the fresh-agent check and the checklist); the owner's
preference edit is a manual step on each account; the managed-settings channel may not exist on the
owner's plan, and the project channel needs a paste per project and per version.

## Delivery mechanisms

Checked on 2026-10-30 against the platform's documentation (code.claude.com/docs; the page is
named in brackets). Where the documentation is partial, it says so.

- **What reaches a session, by level.** The platform's own instructions and the personal
  preferences come first. A `CLAUDE.md` is sent as the first message after them, re-sent with
  every request, and put back from disk after compaction [memory; context-window]. A file read
  with a tool is ordinary conversation: after compaction only a handful of recently changed files
  are read again, and one over about 5,000 tokens comes back as a path only [context-window].
- **The current path is undocumented** and depends on the session's network allowing GitHub
  [cloud-environments]; it works today.
- **Size guidance.** Under 200 lines per instruction file; longer files "reduce adherence"
  [memory]. The platform warns at start-up when a file is over the recommended length.
- **Channels that put the core at the `CLAUDE.md` level**, and what each needs:
  - a) **A managed `CLAUDE.md` in the organisation's settings** (Organization settings, Claude
    Code, Managed settings on claude.ai; Owner role). Reaches terminal, desktop, web and cloud
    sessions; not Cowork. One paste by the owner per handbook version. The mechanism is
    documented; that this exact setting works from the web settings page is documented only in part
    [server-managed-settings; memory; model-config]. Whether the owner's plan shows the page is
    unknown; the owner sees it in one click.
  - b) **A claude.ai project's instructions**, at most 16,000 characters, reach every thread
    started in that project at the level of the platform's rules [claude-projects]. One paste per
    project and per version. Offered on Pro, Max and Ultra; not on Team or Enterprise yet.
  - c) **A hook in each of our own repositories** (a small script the platform runs at the start
    of a session) that fetches the core and prints it at start and again after compaction. Capped
    at 10,000 characters; needs a small settings file in each repository, which reverses part of
    the decision of 3 October that removed hooks, and never goes into a client's repository
    [hooks; cloud-environments].
  - d) **An import from a `CLAUDE.md`** cannot point at a web address, and sessions on claude.ai
    do not read the personal `~/.claude/CLAUDE.md`, so this would need a copy of the handbook in
    each repository, which the handbook forbids [memory; cloud-environments].
- **What this means for the plan.** Channel a) takes the 20,000-character core as it is; b) needs
  it condensed to 16,000; c) to 10,000. The downloaded file stays as the fallback for every
  session type and carries the rest.
- **Proving it.** The platform's plugin evaluation runs scripted prompts in a fresh session with
  automatic checks of each reply's shape; it tests a plugin, not a `CLAUDE.md`, so the core would
  be packaged as a plugin for the test [plugin-evals]. Step 5 can use it or a second agent by hand.
